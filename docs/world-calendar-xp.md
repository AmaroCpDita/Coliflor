# Calendar and shared streak XP (migration 021)

Apply `supabase/migrations/021_world_calendar_xp.sql` after migrations 013–020, then deploy the frontend. The migration is transactional and replayable. Do not replay an older rollout afterward: it would restore old reward functions. Migration source is `supabase/calendar-xp-core.sql`; regenerate the complete migration with `node scripts/build-calendar-xp-migration.mjs` after source changes.

For the user's requested fresh integration, run **`supabase/launch-calendar-world-from-zero.sql` instead of 021 alone**, after 020. It includes 021 and an admin-only reset scoped to Amaro/Javiera's existing couple ID. It backs up and empties only the world (inventory, placements, world reward claims, visits and welcome), then starts level 1, zero XP and the forest. All other application tables remain intact. Its stable integration reset key prevents a repeat execution from erasing newly earned progress. A missing target world aborts the transaction. Activation is the actual SQL execution time, not the chat time.

The exact activation timestamp excludes existing records from the activation day; editing an existing calendar record does not make it new. Future dates, including previously planned events, may earn credit when they occur. Recovery photos for dates before the start do not grant XP. Both photos on activation day must have been uploaded after the cutoff. New worlds also receive an exact timestamp cutoff. The date field enforces Santiago calendar dates; the timestamp handles the partial first day.

Daily calendar reward per couple: nos_vimos 70, cita 100, viaje 150, aniversario 150, nota 0. Take the highest category, never add events or partners. Only the earliest elapsed special date of each month receives 150; other special dates count as normal encounters (70). Editing/deleting that date transfers the bonus to the remaining earliest special date. A multi-day trip must have one record per date.

Both partners' photos for a date give 15 additional XP. Recovery records alone give nothing; both original or recovery photos must exist. Deleting a photo removes that date's streak credit until it is complete again. Dates before activation or world creation do not earn retroactive XP. Existing XP is preserved. Future dates are reconciled on source writes, world load, focus and once a minute while the world is open. There is no background scheduler; future points appear on the next reconciliation.

An RLS-protected ledger records calendar/streak rewards by couple, world epoch and date. BEFORE triggers lock the world state before source writes; AFTER triggers recompute all affected source dates under that lock. The authenticated sync RPC also uses the same lock. This serializes partner requests and prevents duplicates. Corrections change total lifetime XP and recalculate level upward or downward. Earned items, placements and opened biomes remain. Existing unique catalog claim keys prevent duplicate level rewards after a rollback. Future unlocks still follow existing biome level thresholds.

Daily gifts still give objects, with zero XP. Placement/interactions give zero XP. The old multiplier RPC returns 1. Forest completion retains level 21 and five goals but removes the 56-day visit gate; shared care requires three distinct visits per member. With six simple meetings, three dates, one special day and 30 complete streak dates, a month gives 1,320 XP: the 3,954-XP forest is approximately three months. Later biomes retain their existing thresholds; this does not promise three months for every biome.

Checks: `npm run build`, `node scripts/check-calendar-xp.mjs`, `node scripts/check-world-editor.mjs`, `node scripts/check-world-catalog-sql.mjs`. SQL checks use an isolated local PGlite installation under tmp.local/sql-check. The new test covers duplicate partner records, maximum category, deletions, category/date changes, rollback, retained inventory, catalog idempotency, recovery photos, future dates, monthly special cap, activation boundary and permissions. Actual simultaneous multi-session behavior and remote migration application require PostgreSQL/Supabase access; PGlite tests execute sequentially.
