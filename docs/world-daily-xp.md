# Daily XP and mobile HUD

Migration 018 replaces the accumulated streak XP with a daily multiplier. Both couple members must have a `streak_photos` record dated today in Santiago. The multiplier is 2 for subsequent XP grants that day, otherwise 1, regardless of current/max streak length. Yesterday's photos and recovery records do not activate it. A daily reward claimed before activation remains claimed; activating the streak cannot duplicate or retroactively boost that claim.

Daily reward: 15 base XP, 30 with x2, one claim per couple per date and one eligible object copy. Interactions: 5 base XP per object type per date, shared daily budget 10 base XP (20 with x2). First placement: 5 base XP per object type once, shared daily budget 15 base XP (30 with x2). Multiple copies, replacing objects and the partner repeating an action do not duplicate credit. If the multiplier activates partway through a date, previously awarded XP counts against the boosted budget.

Historical milestone claims are no longer called when opening the world. The old RPC stays as an authorized no-op for older clients. Clients cannot invoke `grant_world_xp` with arbitrary XP or reward items: its execution is revoked from PUBLIC, anon and authenticated. Authorized server reward functions use it internally; the client uses `interact_world_object`, which verifies the object belongs to the couple's current biome and calculates the reward on the server.

The curve remains 3,954 XP to level 21. Daily reward plus capped interactions gives at most 50 XP per regular active day, plus finite first placements. Frequent complete daily use is approximately 10–12 weeks; this is an estimate, not a promise. The forest still requires at least 56 distinct visiting dates and all five goals, in addition to level 21. Occasional play takes longer.

Apply the complete `supabase/forest-rollout.sql` after 015, or `supabase/migrations/018_world_daily_boost.sql` if 017 is already applied. The combined file is atomic and safe to replay. This migration changes future rewards and marks progression version 4; it preserves existing levels, objects, layouts and open biomes.

The user subsequently authorized recalculating their own existing levels and closing the premature garden. Run the complete `supabase/recalculate-my-world.sql` in the SQL Editor: it includes 016–019 and the selected repair in one transaction. If exactly one world exists it selects that world; otherwise it raises an exception without committing any change and requires the user's couple_id in `v_couple_id`. It never automatically repairs other couples. The admin function cannot be executed by authenticated or anonymous clients. A world that has already completed the forest is rejected.

The repair replays positive daily, placement and interaction activity against current shared/type/day limits, omitting all streak XP and other sources. Historical x2 requires surviving photo records from both members uploaded before the activity. Missing old photo proof grants only base credit; XP is never increased above the logged grant. An old removed object's identity uses its logged object ID when no type survives. Every item's inventory quantity, placed position/scale/orientation, claimed reward, visit and streak is preserved. The couple returns to the forest with other biomes locked until completion. An admin-only audit table records the before/after state; a successful repair runs once and replay cannot erase new XP. Deployment is pending the user's manual SQL execution.

UI: messages wrap within a 16px viewport margin; the diary is a book icon in the action row; empty hammer mode has no instruction banner. A small “×2 hoy” marker appears after 018 is active when both photos are present today. Realtime photo updates, focus and the Santiago date change refresh this status. Reward dialogs also wrap long item names and scroll within the viewport.

Verification: production build; editor/catalog checks; isolated PostgreSQL execution of 013–018 and full rollout, including no retroactive milestones, one/both photos, daily idempotency, couple-wide caps, copy farming prevention, expiration, authorization and replay. Mobile browser checks at 320px and 390px verify the claimed-reward toast stays inside the screen, diary alignment and no empty hammer banner, along with existing touch editing checks. Remote authenticated behavior still requires the user to run the query.
